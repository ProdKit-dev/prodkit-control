# ProdKit Control v0.4.0

ProdKit Control v0.4.0 adds the high-availability and scale control-plane layer while preserving the non-replay safety of externally visible actions.

## Added

- canonical `FencedLease`, `DurableWorkItem`, `LeasedWorkItem`, `QueueSnapshot`, and `CapacityEnvelope` contracts;
- provider-neutral `LeaseStore` and `DurableWorkQueue` ports;
- standalone in-memory fenced lease and bounded recoverable queue implementations;
- PostgreSQL fenced lease and durable work queue implementations with database-clock expiry, transactional ownership, and `SKIP LOCKED` worker acquisition;
- global and per-tenant concurrency admission control;
- graceful runtime lifecycle with accepting, draining, and stopped states;
- recoverable scheduler integration with bounded retry/dead-letter behavior;
- TypeScript representations of the HA contracts;
- additive PostgreSQL schema migration 0005;
- published capacity/backpressure envelope and HA deployment guidance;
- ADR 0001 separating recoverable scheduler leases from permanent external-action idempotency ownership.

## Reliability and safety

- concurrent contenders elect one active lease owner;
- every takeover receives a strictly larger fencing token;
- stale and expired owners cannot renew, release, complete, or retry work;
- durable-work idempotency treats retry policy as immutable in both standalone and PostgreSQL profiles, so the same key cannot silently acquire different `max_attempts` semantics;
- queue admission is bounded and overload fails explicitly;
- retry budgets are bounded and exhausted work is dead-lettered;
- API/runtime draining rejects new work while admitted work can finish within the grace period;
- PostgreSQL lease decisions use the database clock rather than independent replica clocks;
- control-plane failover does not turn an uncertain action result into automatic external-effect replay.

## External-effect guarantee boundary

Fencing protects scheduler ownership; it does not manufacture exactly-once behavior in an arbitrary external system. Automatically replayable externally effectful work must use provider-enforced idempotency, destination fencing/version preconditions, or an equivalent operation-specific guarantee. Otherwise an ambiguous result stays owned by the existing action idempotency record and must be reconciled before retry.

The v0.4 qualification suite includes a crash-after-provider-ack scenario using a stable external idempotency identity and verifies that takeover does not create a second effect identity while the stale worker is unable to acknowledge the work.

## Capacity qualification

The reference HA profile is qualified at the published envelope in `docs/operations/capacity.md`, including concurrent ownership races, bounded queue load, failover, stale-fence rejection, and sustained lease churn. These values are a tested safety envelope, not a universal provider-throughput or latency SLA.

## Deployment compatibility

The PostgreSQL migration is additive. Existing v0.3 replicas may remain running while schema 0005 is applied; v0.4 replicas start against schema version 5, become ready, and old replicas are then drained and replaced. Standalone mode remains available without PostgreSQL or any external orchestrator.

## Release gates

v0.4.0 is releasable only when the exact candidate passes:

- Python 3.12, 3.13, and 3.14 CI;
- Node.js 22 and 24 CI;
- PostgreSQL 18 durable-store tests;
- concurrency/race tests;
- in-flight failover and stale-fence tests;
- bounded load and soak qualification at the published envelope;
- proof that the tested failover path does not duplicate an external-effect identity;
- Security and CodeQL;
- Trusted Release Proof;
- immutable release publication and independent release verification.
