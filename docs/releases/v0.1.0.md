# ProdKit Control v0.1.0 — Hardened execution

Released: 2026-08-21

`v0.1.0` is the hardened-execution milestone for ProdKit Control. It moves externally visible action execution from a process-local reference path to a fail-closed profile with durable PostgreSQL ownership, explicit uncertainty, authenticated tenant scope, isolated credential leases, digest-bound approvals, encrypted evidence storage, and production-oriented executor boundaries.

## Shipped scope

### Durable execution state

- PostgreSQL-backed run projection, event ledger, tenant-scoped idempotency ownership, and execution-attempt journal.
- Ordered schema migrations through schema version `3`, including runtime compatibility metadata and the durable run store.
- Broker-owned execution-attempt identifiers allocated before side effects.
- Explicit `claimed -> started -> succeeded|failed|uncertain` attempt transitions with immutable identity fields and terminal-state guards.
- Ambiguous executor failures retain the idempotency claim and record an `uncertain` attempt; automatic duplicate execution is refused.
- Real PostgreSQL 18 CI proof covers migration application, schema compatibility, durable run/event recovery, tenant-scoped idempotency, and crash-after-start uncertainty recovery.

### Authorization, approval, and credentials

- OIDC/JWT principal resolution validates signature, issuer, audience, expiry, subject, tenant, actor kind, and roles; protected API routes fail closed when authentication is not configured.
- API actions and approvals are bound to the authenticated tenant and actor.
- Approval resolution is bound to action digest, target digest, policy decision/revision, tenant, environment, role, and expiry.
- External approval and credential-broker adapters require HTTPS by default.
- Short-lived credential leases are issued to executor workload identities; the control plane carries only a non-secret credential reference.
- Credential leases are revoked after execution; ambiguous execution or revocation failure is recorded as uncertainty rather than silently retried.

### Evidence and executor boundaries

- AES-256-GCM encrypted filesystem artifact storage with authenticated ciphertext, content-addressed plaintext digests, tenant partitioning, redaction envelopes, atomic writes, and retention metadata.
- Hardened executor implementations for filesystem, Git, GitHub, and HTTP actions with explicit operation/target validation and broker-owned attempt integration.
- The durable broker rejects executors that do not implement attempt ownership; credential-enabled profiles additionally require the credential-lease-aware executor contract.
- Existing package placeholders for database, Kubernetes, and deployment executors are **not** part of the `v0.1.0` supported production executor allowlist and are not represented as completed integrations.

### Release and supply-chain control

- CI, Security, CodeQL, Trusted Release Proof, Release, and Release Metadata callers are thin consumers of the centralized `ProdKit-dev/prodkit-workflows` lifecycle pinned to immutable commit `877aefdeaa2084b47f4867dc6c7b0dfe6525fb2c`.
- Runner selection is resolved centrally, including trusted self-hosted fallback when GitHub-hosted capacity is unavailable.
- Release publication requires successful CI, Security, and CodeQL on the exact `main` SHA plus a successful manually dispatched Trusted Release Proof for that same SHA.
- Trusted Release Proof reruns Python quality/tests/security, PostgreSQL 18 durability proof, Node audit/typecheck/build, release-contract verification, package builds, and artifact inspection without mutating tracked source.
- Publication builds distributions, generates checksums/SBOM evidence and attestations, verifies immutable source identity, and publishes `ProdKit Control v0.1.0` from tag `v0.1.0`.

## Operational database contract

Apply the PostgreSQL migrations in lexical order:

1. `0001_initial.sql`
2. `0002_hardened_execution.sql`
3. `0003_run_store_and_schema_metadata.sql`

A production process must call the schema compatibility guard before accepting control-plane traffic. The runtime fails closed if the database schema metadata is missing, behind, or ahead of schema version `3`.

The execution ledger, idempotency ownership, and attempt journal are operational evidence. After externally visible execution has started, rollback must not delete or rewrite those records. Prefer a forward-fix release and compatible migration. If application rollback is unavoidable, stop new execution first, preserve the database and encrypted evidence store, and run only a binary that explicitly supports schema version `3`.

## Release gates

The release candidate is not publishable until all of the following are true on the exact prepared source:

- Python 3.12, 3.13, and 3.14 CI passes.
- Node 22 and 24 typecheck/build/package validation passes.
- PostgreSQL 18 migration and durability proof passes.
- dependency/security audit and secret/SBOM gates pass.
- CodeQL passes for Python, JavaScript/TypeScript, and GitHub Actions with zero policy-disallowed findings.
- crash-after-start uncertainty and duplicate-delivery/idempotency tests pass.
- API authentication and tenant-scope regression tests pass.
- release metadata and package versions are exactly `0.1.0`.
- an exact-source Trusted Release Proof passes on the current `main` SHA before publication.

## Supported production profile

A production deployment of this milestone is expected to provide:

- PostgreSQL for durable run/event/idempotency/attempt state;
- a configured OIDC principal resolver;
- a fail-closed policy engine;
- an external approval provider when policy requires approval;
- a workload credential broker for privileged executors;
- an encrypted artifact-store key supplied by a deployment secret/KMS boundary;
- only executor implementations explicitly admitted to the deployment allowlist.

The default in-memory FastAPI service graph remains a development/test reference. It is not the durable production profile.

## Non-goals

`v0.1.0` does not claim delivery-chain reconciliation (`v0.2.0`), signed/interoperable provenance (`v0.3.0`), or completion of placeholder database/Kubernetes/deployment executor packages. Those milestones remain governed by `ROADMAP.md`.
