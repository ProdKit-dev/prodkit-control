# ProdKit Control v0.9.0

## Cumulative completeness and language-neutral authority

v0.9.0 is a corrective cumulative-completeness milestone. It closes implementation gaps that remained in first-party package surfaces inherited from the v0.0-v0.8 roadmap and makes portable semantics independent of Python and TypeScript.

This release does **not** rewrite or move the immutable v0.8.0 release. Instead, v0.9.0 makes the repository's current supported surface agree with the roadmap rule that a milestone is not complete merely because a package or adapter boundary exists.

### Completed first-party surfaces

The release provides substantive implementations for the previously scaffolded database, Kubernetes, and deployment executors; OpenAI, Anthropic, Google, and Pydantic AI provider adapters; E2B, Permit, Teleport, and Temporal integrations; and functional `@prodkit/control-next` and `@prodkit/control-react` packages. Existing first-party core, executor, integration, provider, reconciler, and TypeScript packages are version-aligned at v0.9.0 and covered by a machine-discovered package-completeness contract.

Optional provider and integration packages remain optional at runtime. Their optional status means ProdKit Control does not depend on the external service; it does not mean the first-party adapter may be an empty shell.

### Language-neutral semantic authority

Normative portable behavior now lives under `contracts/` as specifications, protocol boundaries, canonicalization profiles, and shared conformance vectors. Python and TypeScript are independent native implementations and are not semantic sources of truth.

The v0.9 portable profiles include deterministic `prodkit-json-v1` canonicalization and the default/conjunctive Control policy semantics. Shared vectors are executed independently by Python and TypeScript CI paths. External policy systems such as OPA and Permit remain adapters to the ProdKit Control policy contract rather than becoming the canonical policy language.

### Release assurance

The release source tree fails qualification if:

- an actual first-party package is missing from the completeness contract or a declared package disappears;
- a first-party package remains scaffold-only or has a version different from the release;
- the language-neutral authority index/specifications/conformance vectors are absent;
- Python and TypeScript diverge from the shared portable vectors;
- the frozen Python or Node dependency graph is stale;
- normal CI, Security, CodeQL, release metadata, exact-source trusted proof, publication, or independent release verification fails.

### Claim boundary

v0.9.0 closes cumulative implementation and semantic-portability gaps. It is **not** the Production Candidate milestone and does not expand v1.0 assurance claims. The former Production Candidate milestone is now v0.10.0 and retains its soak, upgrade/rollback, disaster-recovery, isolation, operational, and independent-review gates.
