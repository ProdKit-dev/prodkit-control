# ProdKit Control v0.3.0

## Portable assurance and interoperability

v0.3.0 makes ProdKit Control evidence portable across organizations, tools, and offline verification boundaries without weakening the canonical control-plane trust model.

### Added

- in-toto Statement v1 interoperability and SLSA provenance-v1 predicate support.
- A versioned ProdKit evidence predicate carrying run identity, tenant identity, evidence-manifest digest, final event hash, and canonicalization metadata.
- Standalone Ed25519 signed checkpoints with explicit signer/key identity, validity windows, revocation semantics, previous-checkpoint chaining, and independently supplied trust-root policy.
- Assurance profiles that can require signing, minimum retention duration, and accepted immutable-retention modes.
- Portable evidence packages containing the evidence bundle, attestation, checkpoint, trust-root metadata, and retention-lock receipt with per-member SHA-256 verification.
- A hardened Sigstore/Cosign integration boundary supporting key-based and keyless verification, certificate identity/issuer constraints, custom trust roots, offline verification, bounded execution, and fail-closed process handling.
- MCP and framework-neutral agent adapters that transform tool/function calls into deterministic `ActionSpec` proposals while preserving ProdKit policy, approval, credential, execution, observation, and evidence ownership.
- Fail-closed conjunctive policy composition for organization-owned PDPs including OPA/Permit/AuthZen-style adapters.
- Bounded OpenTelemetry semantic projection with canonical correlation attributes and error semantics while keeping telemetry non-authoritative.
- Interoperability fixtures and exported JSON Schemas for the new assurance and standards-facing contracts.

### Assurance and security

- Embedded package keys are never sufficient trust by themselves. Offline package verification requires an independently supplied trust-root policy or independently pinned trust-root digest.
- Signing-key validity, signer identity, signature bytes, revocation time, evidence and attestation digests, checkpoint chain references, retention mode/duration, archive membership, and archive size limits are checked before assurance succeeds.
- Historical signatures can remain valid across key rotation only when the trust-root policy explicitly permits signatures created before revocation.
- A signature created at or after the key's revocation time is rejected.
- Required signing or immutable-retention controls fail closed when absent or unverifiable.
- Ordinary local filesystem retention is not represented as compliance-grade WORM retention.
- MCP or agent-supplied annotations cannot choose effect class, risk class, executor identity, operation, or production target scope; those remain administrator-owned bindings.
- External policy engines cannot weaken a stricter decision. `DENY` dominates `REQUIRE_APPROVAL`, which dominates `ALLOW`; conflicting constraints deny.
- OpenTelemetry remains an operational projection only and is never accepted as canonical execution or assurance evidence.

### Compatibility

ProdKit targets the stable wire identifiers `https://in-toto.io/Statement/v1` and `https://slsa.dev/provenance/v1`. Externally versioned interoperability models tolerate unknown compatible fields so newer producers can be verified when the stable contract remains valid. Authoritative ProdKit trust-root, checkpoint, retention, and assurance contracts remain strict.

The v0.3 verifier accepts the v0.2 evidence-bundle schema and wraps it with v0.3 cryptographic assurance, providing an explicit cross-version verification path instead of forcing evidence migration.

### Release gates

The v0.3.0 source is releasable only after all of the following are evidenced on the exact candidate:

- independent offline evidence-bundle/package verification;
- two-key rotation and revoked-key rejection tests;
- fail-closed required-signing and required-retention tests;
- cross-version v0.2 evidence verification under v0.3 assurance;
- in-toto, SLSA, Sigstore, MCP/agent, policy, and OpenTelemetry interoperability fixtures/tests;
- exported schema drift checks for the new public contracts;
- CI, Security, and CodeQL success on the exact release candidate;
- CI, Security, and CodeQL success on the exact merged `main` source;
- exact-source Trusted Release Proof before publication;
- immutable `v0.3.0` tag, published checksums/SBOM evidence, and independent Release Verification after publication.

### Release scope

v0.3.0 is the roadmap's attestations-and-interoperability milestone. High availability, distributed fencing, concurrency/failover guarantees, and sustained-scale validation remain v0.4.0 work. Multi-tenant enterprise isolation beyond the already enforced tenant-bound contracts remains governed by later roadmap milestones and must not be inferred from this release.
