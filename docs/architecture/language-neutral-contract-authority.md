# Language-neutral contract authority

ProdKit Control is not Python software with TypeScript bindings and is not TypeScript software with Python bindings. It is a set of portable control, evidence, lineage, policy, and protocol semantics with independent native implementations.

## Authority hierarchy

Portable semantics are authoritative in this order:

1. language-neutral semantic specifications under `contracts/specifications/`;
2. published/versioned schemas under `schemas/`;
3. protocol-family definitions under `contracts/protocols/`;
4. canonicalization profiles;
5. golden/adversarial conformance vectors under `contracts/conformance/`.

Python and TypeScript implementations are downstream of that authority. Runtime code may implement or optimize semantics but cannot redefine them merely because the implementation language behaves differently.

```text
semantic specifications
        |
published schemas + protocols
        |
canonicalization profile
        |
shared conformance vectors
        |
        +-------------------+
        |                   |
        v                   v
 Python native runtime   TypeScript native runtime
        |                   |
        +---------+---------+
                  |
          same portable meaning
```

## Portable versus runtime-specific behavior

Portable behavior includes security-critical record meaning, canonical identities, declared deterministic policy semantics, protocol/state-machine behavior identified as portable, compatibility rules, and fail-closed handling of unknown or missing required information.

Runtime-specific behavior can include framework adapters, subprocess mechanics, database drivers, browser APIs, HTTP clients, SDK ergonomics, concurrency primitives, or other host-language details. Such behavior must project into portable records at the control/evidence boundary when it participates in an assurance claim.

## Policy architecture

ProdKit Control owns a language-neutral policy-decision vocabulary and fail-closed composition profile. It does not require one policy engine or universal policy language.

Organization engines such as OPA, Permit, Cedar-style systems, cloud IAM, or future providers are adapters:

```text
organization policy systems
     |        |        |
    OPA    Permit    other
     |        |        |
     +--------+--------+
              |
        normalized decision
              |
              v
  ProdKit portable policy contract
              |
       fail-closed composition
              |
              v
      execution authorization
```

An adapter cannot turn a stronger normalized decision into a weaker one. `deny` dominates `require_approval`, which dominates `allow`; conflicting constraints deny by default.

## Cross-runtime conformance

A semantic claim is portable only if every native runtime claiming it passes the same conformance corpus. v0.9 therefore runs the same canonicalization and policy vectors independently through Python and TypeScript.

The conformance corpus is intentionally independent of runtime test suites. A Python test that proves Python agrees with itself, or a TypeScript test that proves TypeScript agrees with itself, is not cross-runtime evidence.

Future runtimes such as Go, Rust, Java, or another language can join by implementing the same published contracts and passing the same relevant conformance profiles. No existing runtime becomes the semantic parent of the new implementation.

## Schema generation

A schema may be generated by tooling implemented in Python, TypeScript, or another language. The generator is a build mechanism, not normative authority. Once published/versioned, schema identity and compatibility are governed by the language-neutral contract authority and release rules.

Generated artifacts must be checked for drift, and a runtime change that would alter a published portable schema requires the corresponding contract/version decision.

## Release invariant

A release claiming a portable profile must fail if:

- the authority index is missing or names a native runtime as normative authority;
- a required specification/vector is absent;
- Python and TypeScript disagree on shared canonicalization or policy vectors;
- CI no longer executes the authority/conformance gates;
- a security-critical semantic change exists only in one runtime implementation;
- an external provider is treated as canonical authority rather than an adapter.

This invariant is part of the v0.9 cumulative-completeness gate and is inherited by v0.10 and v1.0.
